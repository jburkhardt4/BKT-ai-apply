### S70 — Deterministic **"no console errors / no uncaught page errors"** gate in AI-UAT via `page.consoleMessages()` / `page.pageErrors()` — **no version bump**  ·  [Recommend: IMPLEMENT]

- **What's new:** Playwright shipped first-class, *stored* console/error introspection —
  `page.consoleMessages()` and `page.pageErrors()` (**v1.56**) retrieve the page's captured
  console output and uncaught exceptions directly, and **v1.59** (the "agentic release,"
  Apr 2026) added `page.clearConsoleMessages()` / `page.clearPageErrors()` plus a `filter`
  option on both. No manual `page.on('console' | 'pageerror')` bookkeeping. **All ship in the
  repo's current `1.60.0` — nothing to upgrade.**
- **Why it matters for bk-ai-apply:** the `e2e/ai-uat/` suite asserts that flows *complete* but
  never checks whether the page threw — verified: zero `consoleMessages`/`pageErrors`/
  `console.error` across every spec. A React + Supabase SPA emits its most useful failure
  signals there: failed PostgREST calls, **RLS 401s**, unhandled promise rejections, and React
  hydration/act warnings. A "flow passed" assertion sails right past them. A deterministic
  console/page-error gate catches regressions the flow and (still-open, S01) pixel checks miss —
  cheap, deterministic, exactly the release-safety layer JB prioritizes.
- **Concrete change (narrow):** in `e2e/ai-uat/_helpers/setup.ts`, add a shared fixture /
  `afterEach` that reads `page.pageErrors()` and `page.consoleMessages({ filter: … })`
  (error-level only) and fails the test if either is non-empty, with a small per-spec allowlist
  for known-benign noise. Turn it on in **`smoke.spec.ts` first** (gate the happy path), then
  widen spec-by-spec. No dependency bump (1.56/1.59 APIs already in 1.60); no CI/secret changes.
- **Source(s):** Playwright release notes — **v1.56** (`page.consoleMessages()` / `page.pageErrors()`)
  and **v1.59** (`clearConsoleMessages` / `clearPageErrors` + `filter`), Apr 2026 —
  playwright.dev/docs/release-notes.
- **Recommend:** **IMPLEMENT** — genuine, verified gap; narrow, no upgrade, reversible. Distinct
  from S30 (axe/WCAG a11y) and S01 (pixel snapshots). *(Landing it as a PR needs a live GitHub
  connector — see Blocker.)*

### S71 — Playwright **`browser.bind()`** (v1.59): one shared, observable browser for the *local* agentic loop (`playwright-cli` / `@playwright/mcp`)  ·  [Recommend: TRACK]

- **What's new:** Playwright **v1.59** added `browser.bind(name, opts)` → returns an endpoint
  that makes a *launched* browser available for `playwright-cli`, `@playwright/mcp`, and other
  clients to connect to; `playwright-cli` auto-binds its browsers "so you can see what your
  agents are doing." Present in the repo's `1.60`.
- **Why it matters for bk-ai-apply:** CI AI-UAT runs headless (Browserbase/Stagehand), but the
  *local* Claude Code dev loop has no shared, watchable browser — when the `qa-uat` / `feature-dev`
  agents drive a browser via MCP, JB can't see or take over the same session. `browser.bind()`
  lets one visible Chromium be shared between `playwright-cli`, `@playwright/mcp`, and the
  interactive loop, so agent actions are observable and human-takeover is possible mid-run. This
  is the local-dev observability tier that complements (not replaces) the Browserbase CI path,
  and is distinct from S25 (adopt Playwright MCP a11y-tree) and S59 (desktop built-in browser).
- **Concrete change (exploratory):** no repo change yet — spike a local flow: launch via
  `playwright-cli` (or a small script calling `browser.bind('bkt-loop')`) and point
  `@playwright/mcp` at the returned endpoint in the loop's `.mcp.json` (S32); confirm the
  `qa-uat` agent and JB share one browser. Document as the local interactive UAT/visual tier.
- **Source(s):** Playwright **v1.59** release notes — `browser.bind()`
  (playwright.dev/docs/api/class-browser#browser-bind; playwright.dev/docs/release-notes),
  Apr 2026.

### S74 — Migrate off legacy `anon` / `service_role` to Supabase **Publishable / Secret API keys** (hard deprecation end-2026)  ·  [Recommend: TRACK]

- **What's new:** Supabase is replacing the legacy JWT-based **`anon`** and **`service_role`** keys
  with **publishable (`sb_publishable_…`)** and **secret (`sb_secret_…`)** API keys. New projects
  since **Nov 1 2025** no longer get legacy keys; monthly migration reminders are going out; and
  **legacy keys are deprecated by end-2026** and will eventually be deleted — apps still on them will
  break. Both key types work **simultaneously**, so migration is incremental and non-breaking, and
  secret keys can be created/rotated/revoked individually (unlike the single static `service_role`).
- **Why it matters for bk-ai-apply:** this touches the **auth boundary** and the **single DB client**
  non-negotiable (`src/lib/supabase.ts`), plus any `service_role` usage in Edge Functions — a
  hard-deadline production item *this year* for a deployment lead. Migrating now (while both keys work)
  de-risks a forced cutover and unlocks per-key rotation/revocation, strengthening auth posture
  without touching RLS.
- **Concrete change (narrow, staged):** inventory where `anon`/`service_role` are read (client env in
  `src/lib/supabase.ts`; Edge Function secrets); create `sb_publishable_*` + `sb_secret_*` in the
  dashboard **alongside** the legacy keys; swap the **client** to the publishable key first (lowest
  risk, RLS unchanged), then move Edge Functions to a scoped secret key; keep legacy keys enabled
  until verified, then disable. No RLS/policy changes; stage behind review, never `main` directly.
- **Source(s):** Supabase Docs — **"Migrating to publishable and secret API keys"**
  (supabase.com/docs/guides/getting-started/migrating-to-new-api-keys) and "Understanding API keys";
  Supabase changelog/discussion **#29260** "Upcoming changes to Supabase API Keys."
- **Recommend:** **TRACK** — auth-boundary change; agree the staged cutover with JB. Distinct from
  S17 (secret scanning) and S47 (Data API exposure).
