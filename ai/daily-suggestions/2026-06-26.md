### S30 — Add a deterministic WCAG gate with `@axe-core/playwright` (rule-based a11y, not vision)
- **What's new:** `@axe-core/playwright` injects axe-core into a real browser page and
  asserts against **WCAG 2.0/2.1/2.2** rules (color contrast, missing form labels,
  bad ARIA, broken keyboard/focus order), returning violations with the exact selector
  and severity. `AxeBuilder.withTags(['wcag2a','wcag2aa','wcag21aa','wcag22aa'])` scopes
  a scan to the criteria you choose, and the build fails on any violation. It is, in
  2026, the lowest-friction automated-a11y stack on top of Playwright.
- **Why it matters for bk-ai-apply:** every a11y signal in the repo today is
  **non-deterministic or structural** — AI-UAT is Stagehand/LLM vision (`retries: 0`),
  S19 (ARIA snapshots) asserts *structure*, S25 (Playwright-MCP a11y-tree) is for *agent
  navigation*, S21 (Chrome DevTools MCP) is *interactive*. None of them assert WCAG
  *rules*. A small axe pass over the core authenticated routes (dashboard, pipeline
  board, application detail) gives a fast, free, repeatable regression gate that catches
  the ~30–40% of WCAG issues software can catch — the deterministic complement to the
  LLM UAT. No axe/Lighthouse dependency exists in `package.json` today.
- **Concrete change (narrow):** `pnpm add -D @axe-core/playwright`; add one
  `@a11y`-tagged spec under `e2e/` (e.g. `e2e/a11y/core-routes.a11y.spec.ts`) asserting
  `expect(results.violations).toEqual([])` for `wcag2a`+`wcag2aa` on 2–3 routes; add a
  `test:a11y` script and run it under the existing **opt-in** `RUN_E2E` job in `ci.yml`
  (it needs the same `VITE_SUPABASE_*` env), so it skips-not-fails until secrets exist.
  Start in report-only mode for one run, then flip to failing.
- **Sources:** [Accessibility testing — Playwright (playwright.dev)](https://playwright.dev/docs/accessibility-testing);
  [Playwright Accessibility Testing with Axe — Complete 2026 Guide (qaskills.sh)](https://qaskills.sh/blog/playwright-accessibility-testing-axe-complete-guide) (2026).
- **Recommended action: TRACK** — verified gap, but it adds a dependency + new specs
  wired into the auth'd e2e harness; pilot report-only on core routes before gating.

### S31 — Add a Lighthouse-CI performance/Core-Web-Vitals **budget gate** on Vercel previews
- **What's new:** the **Lighthouse CI Action** (`treosh/lighthouse-ci-action`, on top of
  `GoogleChrome/lighthouse-ci`) audits a deployed URL on every PR and **fails the build**
  when a `budget.json` assertion is exceeded (LCP/CLS/TBT, total byte weight, request
  counts). It reads the Vercel **preview URL** and posts the scores as a PR comment;
  GitHub's Ubuntu runners ship Chrome, so no extra browser install. April-2026 write-ups
  position perf budgets in CI/CD as table stakes for shipping React/Vite apps.
- **Why it matters for bk-ai-apply:** CI today gates only `validate` (typecheck · lint ·
  vitest) plus an opt-in Playwright `e2e` job — there is **no performance or CWV signal
  anywhere**. This is deterministic and budget-based, which makes it distinct from the
  *interactive/agentic* Chrome DevTools MCP (S21) and from *pixel* visual review (S02):
  S31 is a numeric gate that blocks a regression in bundle size or LCP before it reaches
  prod. For a Vite SPA that "throws at init without Supabase env," budget-checking the
  built preview catches shipping-weight regressions the unit tests never see.
- **Concrete change:** add `.github/workflows/lighthouse.yml` triggered on
  `deployment_status` (Vercel preview success) — the same auto-trigger plumbing tracked
  in S03 — running `treosh/lighthouse-ci-action` against the preview URL with a checked-in
  `lighthouserc.json`/`budget.json`. Gate it behind a `RUN_LHCI=true` repo variable
  (mirror the `RUN_E2E`/`RUN_AI_UAT` opt-in pattern) and start with `warn` assertions,
  then promote to `error` once a baseline is set.
- **Sources:** [GoogleChrome/lighthouse-ci (GitHub)](https://github.com/GoogleChrome/lighthouse-ci);
  [Lighthouse CI Action — GitHub Marketplace (treosh)](https://github.com/marketplace/actions/lighthouse-ci-action);
  [How to Set Up Performance Budgets in CI/CD Pipelines (dev.to)](https://dev.to/apogeewatcher/how-to-set-up-performance-budgets-in-cicd-pipelines-lj) (Apr 2026).

### S32 — Promote MCP config to a project-scoped, checked-in `.mcp.json` for the agent loop
- **What's new:** Claude Code resolves MCP servers at three scopes — **local**
  (`~/.claude.json`, private), **project** (`.mcp.json` at repo root, **committed to
  version control**, shared with the team and every Claude Code session), and **user**
  (global). Adding a server with `claude mcp add --scope project` writes `.mcp.json`;
  teammates who clone the repo get an approval prompt and the same servers. It supports
  `${VAR}`/`${VAR:-default}` expansion so config is shareable without committing secrets.
- **Why it matters for bk-ai-apply:** the only MCP config in the repo is
  **`.vscode/mcp.json`** with a single `Jam` server — that file is **editor-specific
  (VS Code / Copilot)** and is **not** what Claude Code reads. The whole point of this
  repo is an agentic Claude Code loop (12 subagents, wave dispatch graphs), yet the loop
  has **no version-controlled MCP surface**: any browser/DB MCP the agents use lives in
  per-machine state, so it isn't reproducible across Codespaces or teammates. A root
  `.mcp.json` makes the loop's tools an auditable, reviewable artifact and is the correct
  home for the browser-MCP decisions still open in S25/S21/S12. This is the *config
  mechanism*; S25 was *which* browser MCP to wire.
- **Concrete change:** add `.mcp.json` at repo root with the existing `Jam` server
  (straight parity with `.vscode/mcp.json`, zero new servers), committed so the loop +
  teammates share it. Each developer's tokens stay in local scope. Land it as the
  canonical place to later add the chosen Playwright/Chrome-DevTools MCP. Keep
  `.vscode/mcp.json` for the VS Code UI or delete it once parity is confirmed.
- **Sources:** [Connect to MCP servers — Claude Code Docs (project scope / `.mcp.json`)](https://code.claude.com/docs/en/mcp-quickstart);
  [Install and Configure MCP Servers in Claude Code, 2026 (systemprompt.io)](https://systemprompt.io/guides/claude-code-mcp-servers-extensions) (2026).
- **Recommended action: IMPLEMENT** — single additive root file at parity with the
  existing Jam server; no new servers, approval-gated by Claude Code, zero app impact.

### S33 — Encode "main is always protected" as a GitHub **ruleset + CODEOWNERS** (protection-as-code)
- **What's new:** GitHub **repository rulesets** (GA) supersede legacy branch-protection
  rules: multiple rulesets stack and aggregate to the most-restrictive outcome, they're
  configurable via the REST API (`pull_request` rule with `require_code_owner_review`,
  `required_approving_review_count`), and they pair with a **CODEOWNERS** file (in `.github/`,
  root, or `docs/`) to require owner review on the paths that matter.
- **Why it matters for bk-ai-apply:** "`main` is always protected … all changes land as
  draft PRs" is a stated **non-negotiable of this very routine**, and the agent dispatch
  graph terminates at a Release-Gate node — but in the snapshot that protection is a
  *convention*, not enforced config: there's **no `CODEOWNERS`** and no ruleset artifact
  in the repo. Encoding it means the autonomous loop (and the gh-aw workflows that open
  PRs — S16) physically cannot merge to `main` without the required PR + review + green
  `validate`. This is distinct from secret-scanning/push-protection (S17) and gh-aw
  hardening (S16): those guard *content*; this guards *the merge boundary*.
- **Concrete change:** add `.github/CODEOWNERS` mapping the safety-critical trees to JB
  (`/supabase/ @jburkhardt4`, `/docs/adr/ @jburkhardt4`, `/.github/ @jburkhardt4`, `* @jburkhardt4`);
  then create a branch ruleset on `main` (UI or REST/`gh api`) requiring a PR, ≥1
  approving review, **review from Code Owners**, and the `validate` status check, with
  force-push/deletion blocked. Export the ruleset JSON into `docs/` so it's reviewable.
- **Sources:** [About rulesets — GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets);
  [Repository Rules are generally available — GitHub Blog](https://github.blog/news-insights/product-news/github-repository-rules-are-now-generally-available/);
  [About code owners — GitHub Docs](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).

### S34 — Normalize subagent `tools:` declarations to Claude Code's canonical names (fix `context-keeper`)
- **What's new:** Claude Code's subagent spec defines `tools` as a **comma-separated
  allowlist of canonically-named tools** (`Read, Write, Edit, Bash, Glob, Grep, …`);
  **omitting the field inherits *all* tools.** Names are matched as written — a malformed
  value doesn't safely "do nothing," it risks resolving to the inherit-everything default.
- **Why it matters for bk-ai-apply:** 11 of the 12 agents declare a tight, correct
  allowlist (e.g. `Release-Gate: Read, Glob, Grep`), but **`.claude/agents/context-keeper.md`**
  uses **`tools: [read, glob, grep, edit, write]`** — lowercase **YAML array** instead of
  the comma-separated PascalCase form. Context-Keeper is the one agent that **writes the
  institutional memory** (ADRs, `business-rules.md`, `lessons.md`), so if that malformed
  list falls back to inheriting every tool, the least-privilege intent on your most
  trust-sensitive writer is silently void. (Orchestrator also has no `tools:` and thus
  inherits all — intended for a dispatcher, but worth a confirming comment.)
- **Concrete change:** one-line edit in `.claude/agents/context-keeper.md` →
  `tools: Read, Glob, Grep, Edit, Write`. Optionally add an explicit comment on
  `orchestrator.md` documenting that full-tool inheritance is intentional for the
  dispatcher. No behavior change for the other 11 agents.
- **Sources:** [Create custom subagents — Claude Code Docs (`tools` field)](https://code.claude.com/docs/en/sub-agents);
  [Claude Code Subagents — Practical 2026 Guide (nimbalyst.com)](https://nimbalyst.com/blog/claude-code-subagents-guide/) (2026).
- **Recommended action: IMPLEMENT** — verified one-file correctness fix that restores
  least-privilege on the memory-writing agent; zero blast radius.
