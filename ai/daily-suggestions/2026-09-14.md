## Suggestion cards

### 1. `claude plugin eval` — the first supported way to prove `/loop` `/routines` `/dispatch` actually work  [Recommend: IMPLEMENT]

**What's new.** CC **2.1.269** (Sep 11 2026) added `claude plugin eval`: run a plugin's eval suite against Claude Code and get **scored, reproducible results** (JSON + HTML report). `claude plugin eval init` has Claude read the plugin, propose cases and graders, pilot them, and write them under `evals/`. Each case runs **three times with the plugin and three times without** — the reported Δ is what the plugin contributes.

**Why it matters for bk-ai-apply.** Theme 2 of this routine has asked for "concrete, testable improvements" to `/loop`, `/routines` and `/dispatch` for 12 weeks, and every card so far has been an *argument* (S06, S45, S83, S158, S192, S207). There has been no way to tell whether a change to those command definitions made the loop better or worse — or whether they still steer correctly after a model swap (JB's default moved Opus 4.6 → Opus 5 in S97, and Fable 5.1 became a shipped default in 2.1.257). This is the missing feedback signal, and it is the same category of instrument as S203's `/usage` Loops breakdown (tokens) and S211's `/skill-doctor` (context tax) — this one measures **outcome**.

**Concrete change.** This makes **S15 (package the agent roster as a plugin) a prerequisite, not a nice-to-have** — `plugin eval` operates on a plugin folder. Narrow path: scaffold a minimal local plugin wrapping only the three commands (2.1.157 auto-loads plugins in `.claude/skills` with no marketplace; 2.1.265 lets `--plugin-dir` point at a folder of plugins and hot-reloads children), run `claude plugin eval init`, and seed 3–5 cases against the repo's own non-negotiables — e.g. "stage change writes an `application_events` row", "no direct DB access outside `src/lib/supabase.ts`", "`pnpm validate` run before declaring done". Graders are pass/fail: regex on the reply, whether a specific tool was called, or a rubric judged by a second model. Run in a **fresh** session (S192). Commit `evals/` so the suite is diffable.

**Watch.** Six runs per case is not free; scope the suite small and read the Δ, not the absolute score.

**Sources.** Claude Code changelog 2.1.269 (Sep 11 2026); [Test plugins with evals — Claude Code Docs](https://code.claude.com/docs/en/plugin-evals).

### 2. CC 2.1.270 — running target `>=2.1.270`; **do not run 2.1.269** on the unattended loop  [Recommend: IMPLEMENT]

**What's new.** CC **2.1.270** (Sep 12 2026) is a single-line release: *"Fixed read-only git commands in Bash unexpectedly asking for permission after a session had been running for a while (regression in 2.1.269)."*

**Why it matters for bk-ai-apply.** This is a regression whose blast radius lands squarely on this routine's own design. A long-running unattended `/loop` is precisely "a session that has been running for a while", and read-only git commands (`git status`, `git log`, `git diff`) are what every loop iteration does constantly. Under the S210 recommendation (`--permission-prompts none`), an unexpected prompt is **auto-denied**, so on 2.1.269 the loop would not hang — it would start silently failing its own git probes, which is the harder failure to diagnose in a transcript.

**Concrete change.** Running target `>=2.1.270`. **Security floor stays `2.1.260` (S209)** — 2.1.270 carries no security fix, so `requiredMinimumVersion` does not move. Skip 2.1.269 entirely on any unattended host; take it only for `plugin eval` work in an interactive session, or wait and get both at 2.1.270.

**Sources.** Claude Code changelog 2.1.270 (Sep 12 2026), 2.1.269 (Sep 11 2026).

### 3. `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` — raise `/dispatch` wave width deliberately, not by default  [Recommend: TRACK]

**What's new.** CC **2.1.269** added `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` (range **1–256**) to raise the **Workflow tool's per-run** concurrent-agent limit "for inference-bound fan-outs."

**Why it matters for bk-ai-apply.** The `/dispatch` concurrency line has had a session-wide knob (`MAX_CONCURRENT_SUBAGENTS`, S86), a cost mitigation (`CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS`, S141) and a container-CPU correctness fix (S140) — but no **per-workflow-run** ceiling. This is the right granularity for wave orchestration: audit waves are inference-bound and could widen, while migration waves touching shared files must stay narrow.

**Concrete change.** Do **not** raise it globally. Set it per workflow definition, and only for waves that satisfy the S193 design constraints (disjoint file scopes, one success criterion). Record the chosen width and its justification alongside the S07 dynamic-workflow notes. Note the tension: S193's finding was that merged-PR fraction *falls* as agent count rises — more width is not more throughput.

**Sources.** Claude Code changelog 2.1.269 (Sep 11 2026).

### 4. `maxEffortLevel` — a cost ceiling for the scheduled loop that survives model changes  [Recommend: TRACK]

**What's new.** CC **2.1.267** (Sep 9 2026) added **`maxEffortLevel`**, settable top-level or per-model under `modelSettings`, capping the effort level **on every provider** including Bedrock, Vertex and Foundry; users can still choose a lower level. Same release added `--system-prompt-snapshot off` (render the system prompt fresh each request instead of reusing the conversation's recorded prompt) for iterating on prompt text.

**Why it matters for bk-ai-apply.** The unattended-cost line so far pins *which model* runs (S169 `ANTHROPIC_DEFAULT_MODEL`, S213's four-level subagent ladder) and *how much* it may spend (S181 budget headroom, S203 Loops breakdown), but nothing caps *how hard it thinks per turn* — and effort defaults have moved with model releases before (Opus 4.8 shipped defaulting to high, 2.1.154). A cap makes the scheduled run's cost profile stable across model rolls rather than re-derived every time Anthropic ships a default.

**Concrete change.** Add `maxEffortLevel` to the unattended profile in `.claude/settings.json` (same commit as S201/S203/S209/S213 settings work, still queued on GitHub) and record it in `docs/conventions/model-routing.md` + ADR-010 next to the S169 model pin. `--system-prompt-snapshot off` is the right flag for the S211 `/skill-doctor` and card-1 eval-authoring sessions — it makes prompt iteration take effect immediately instead of reusing a stale snapshot.

**Sources.** Claude Code changelog 2.1.267 (Sep 9 2026).

### 5. CC 2.1.265 — four unattended-loop correctness fixes, including the subagent prompt-cache re-pay S141 was working around  [Recommend: TRACK]

**What's new.** CC **2.1.265** (Sep 8 2026), a large fix release. Four items matter here:

- *"Fixed resuming a foreground-spawned subagent changing its tool list and system prompt prefix, which broke prompt-cache reuse for that agent."*
- *"Fixed agent teammates and resumed subagents moving `SubagentStart` hook context and preloaded skills out of the prompt prefix on later turns, which broke prompt-cache reuse."*
- *"Fixed non-interactive sessions (`-p` with stream-json input, Agent SDK, cloud sessions) resetting the shell working directory at each new user message; a `cd` now persists across turns."*
- *"Fixed resuming a workflow run after its container restarted; a resume whose run journal is missing now fails with a clear error instead of rerunning every agent."*

2.1.269 adds two more cache fixes: partial cache invalidation after a response was cut off at the output-token limit and auto-resumed, and cache reuse damage when resuming a session interrupted mid-thought.

**Why it matters for bk-ai-apply.** The first two are **upstream fixes for the problem S141 mitigated by staggering fan-out**. The stagger reduced the cost of re-paying a broken prefix; these stop the prefix from breaking. Once running `>=2.1.270`, re-measure `/dispatch` wave cost before assuming the stagger is still carrying weight. The `cd`-reset fix is a straightforward unattended-loop correctness bug in exactly the headless mode the scheduled routine runs in. The workflow-resume fix converts a container restart from "silently re-run every agent" (wasted spend, possible duplicate side effects) into a loud error.

**Concrete change.** No config change. Fold into the S210 running-target bump (card 2), then re-baseline `/dispatch` cost against the S203 Loops breakdown and decide whether `CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS` is still earning its latency.

**Sources.** Claude Code changelog 2.1.265 (Sep 8 2026), 2.1.269 (Sep 11 2026).

### 7. Anthropic, "How we contain Claude across products" — the containment line's missing design doc  [Recommend: TRACK]

**What's new to this ledger.** Anthropic Engineering, **May 25 2026**. Predates the rolling window but was never surfaced — same category as S130. Five things it says that change existing cards rather than adding a new one:

- **An egress allowlist is a capability grant, not a destination filter.** "Every function reachable through any domain on an allowlist is now an attack surface." The illustrating incident: Cowork's allowlist correctly permitted `api.anthropic.com`, and a poisoned workspace file used an **attacker-supplied API key** to upload the user's files to the attacker's Anthropic account. The sandbox worked perfectly and the data still left.
- **Persistent memory poisoning** is named as a coming threat class: "product memory, CLAUDE.md files, mounted workspaces, and the state directories of scheduled and long-running agents" — an injection landing in any of these is reloaded every start.
- **Multi-agent trust escalation**: if a sub-agent's output is treated as higher-trust than raw tool output because it "came from us," that is a new injection vector.
- **Symlink resolution must happen *before* path validation**, or a symlink inside an authorized folder escapes it.
- **Measured auto-mode numbers**: ~0.4% of benign commands blocked, **~17% of overeager actions get through** — "one layer of defense-in-depth inside a sandbox, not a substitute for one."

**Why it matters for bk-ai-apply.** The allowlist finding directly modifies the **S98 `sandbox.network.strictAllowlist`** and **S110 Stagehand `setDomainPolicy()`** designs: both are written as destination allowlists, and both would allow `*.supabase.co` — which is a capability grant covering the Storage and Data APIs with *any* key, not just the project's. The memory-poisoning section names three artifacts this repo actually has: a committed `CLAUDE.md`, `.claude/agent-memory/orchestrator/` (S194), and a scheduled-task state directory. The 17% figure is the number the S157/S170 "auto mode in unattended runs" decision has been missing.

**Concrete change.** Amend the S98/S110 lines with the capability-grant framing before either is implemented — allowlist the *narrowest reachable surface*, and treat any domain that accepts caller-supplied credentials as unsafe to blanket-allow. Add the three persistent-context artifacts to the ADR that S191 proposes (agent-config regression evals on `.claude/**` + `CLAUDE.md` changes) as the place a poisoned instruction would be caught. Quote the 17% figure in the S157 decision rather than reasoning about auto mode qualitatively.

**Sources.** [How we contain Claude across products](https://www.anthropic.com/engineering/how-we-contain-claude), Anthropic Engineering, May 25 2026.

### 8. Playwright 1.63 CLI/reporter ergonomics the S214 card didn't cover  [Recommend: TRACK]

The arm64 change removes a browser-build difference between arm64 Codespaces and x64 CI — relevant the moment a visual gate lands (S01, still open).

**Concrete change.** None yet — **the pin still holds at the S214 recommendation: land 1.62.1 (S111) first, then take 1.63.x after a patch.** As of this run there is still **no 1.63.1**. Note `--add-reporter` on the S215 implementation line so the trace/aria reporter work uses the flag rather than a forked config.

**Sources.** [Playwright release notes](https://playwright.dev/docs/release-notes); npm dist-tags for `@playwright/test` (latest still 1.63.0 as of 2026-09-14).
