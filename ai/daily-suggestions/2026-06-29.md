### S47 — Harden the Supabase Data API: set `auto_expose_new_tables = false` in `config.toml`
- **What's new:** Supabase is rolling out a **breaking default change** — tables created in the
  `public` schema are **no longer auto-exposed** to the Data API (PostgREST) and GraphQL API.
  Timeline: **2026-04-28** opt-in at project creation; **2026-05-30** it begins becoming the
  default for new projects (gradual rollout — *already in effect today*); **2026-10-30** it applies
  to **all existing projects** and the `auto_expose_new_tables` flag is **removed**. The CLI flag
  now **resolves to `false` when unset**, matching the new hosted default; new tables then require
  an explicit Postgres `GRANT` before the API can see them (existing tables keep their grants).
- **Why it matters for bk-ai-apply:** this lands directly on **non-negotiables #1 (RLS always on)**
  and **#5 (every query scoped by `user_id`; no cross-user leakage)**. The repo's
  `supabase/config.toml` leaves `auto_expose_new_tables` **commented out (unset)**. Two concrete
  risks: (a) local `supabase db reset` / branch DBs can now **diverge from prod** behavior, and
  (b) the project adds tables often — **34 migrations** already — so a future `public` table could
  be **implicitly exposed locally** while being revoked in prod, exactly the silent
  cross-surface-area gap that "RLS is on" doesn't catch (RLS without a row-returning grant is moot;
  an over-grant is the danger). Setting it explicitly makes exposure a **conscious GRANT decision**
  — defense-in-depth *under* RLS — and is the deterministic backstop the `Supabase-Security` agent
  should assert.
- **Concrete change (narrow):** in `supabase/config.toml`, under `[api]`, set
  `auto_expose_new_tables = false`. Run `supabase db reset` locally + smoke the app and the e2e
  suite; confirm existing tables still resolve (grants unchanged) and that any *new* table now needs
  an explicit `grant ... on table public.<t> to authenticated;`. Pure config — **no data, auth, or
  secret change**; forward-compatible before the 2026-10-30 removal.
- **Sources:** [Breaking Change: Tables not exposed to Data and GraphQL API automatically — Supabase Changelog #45329](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically);
  [Securing your Data API (hardening) — Supabase Docs](https://supabase.com/docs/guides/api/hardening-data-api);
  [Supabase CLI config — Supabase Docs](https://supabase.com/docs/guides/cli/config) (2026).
- **Recommended action: IMPLEMENT** — one-line config on a non-negotiable, additive and reversible;
  verify via `db reset`. No secrets touched.

### S49 — Make the `e2e` gate hermetic with Playwright HAR replay (`routeFromHAR`) so it runs on every PR without live secrets
- **What's new:** Playwright's `routeFromHAR()` / `recordHar` records every request the page makes
  **once** into a HAR archive and **replays it deterministically** on later runs — described as
  *"the lever that turns a flaky, backend-dependent suite into a fast, deterministic one."* Record
  with `{ update: true }`, replay with `{ update: false }`; matching is strict on URL + method
  (+ POST body).
- **Why it matters for bk-ai-apply:** the `e2e` job in `ci.yml` is **gated OFF by default**
  (`if: vars.RUN_E2E == 'true'`) precisely because, per its own comment, *"the SPA throws at init
  without Supabase env"* and it needs live `VITE_SUPABASE_*` secrets. So the strongest deterministic
  gate runs against **nothing** on most PRs. Recording HAR for the read-heavy core flows (auth
  bootstrap → `pipeline` list → `job-fit`) lets the suite replay Supabase/PostgREST + LLM responses
  with **no secrets and no live backend**, so it can run **unconditionally** on every PR. This is
  distinct from the already-tracked **S13** (real per-PR branch DBs) and **S37** (real `seed.sql`):
  HAR mocks the **network**, the cheapest path to an always-on gate, and gives the autonomous AI-UAT
  a hermetic baseline to diff prod behavior against.
- **Concrete change:** add `e2e/.har/` archives recorded once via
  `await context.routeFromHAR('e2e/.har/pipeline.har', { url: '**/rest/v1/**', update: true })`
  (plus the `/auth/v1/**` and LLM/edge endpoints); **scrub tokens** and commit the sanitized HARs;
  in the e2e fixtures replay with `routeFromHAR(..., { update: false })`; then drop the `RUN_E2E`
  guard for the **mocked subset** so it runs on every PR, keeping live-secret e2e as a separate
  opt-in lane. Start with `smoke.spec.ts` + `pipeline.spec.ts`.
- **Sources:** [Mock APIs / `routeFromHAR` — Playwright Docs](https://playwright.dev/docs/mock);
  [How to handle Playwright network interception — oneuptime (2026-02-02)](https://oneuptime.com/blog/post/2026-02-02-playwright-network-interception/view);
  [Playwright network interception & mocking guide — qaskills.sh](https://qaskills.sh/blog/playwright-network-interception-mocking-guide) (2026).
- **Recommended action: TRACK** — recording + token-scrubbing the HARs is a small project; land the
  `smoke` HAR first, then expand and flip the guard.

### S50 — Add security response headers in `vercel.json` (`headers`)
- **What's new:** Vercel **does not inject application-level security headers**; you set them via a
  `headers` array in `vercel.json`. Note the platform nuance: on **`*.vercel.app`** even HSTS must
  be set **explicitly** (custom domains get HSTS auto).
- **Why it matters for bk-ai-apply:** production-readiness / release-safety for an **authenticated
  Supabase app** handling user PII and access tokens. `vercel.json` today carries only `framework`
  + a SPA rewrite — **no `headers`** — so responses ship without `Strict-Transport-Security`,
  `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `X-Frame-Options`/`frame-ancestors`
  (clickjacking), or `Permissions-Policy`. The app deploys to **`bkt-ai-apply.vercel.app`** (per
  `ai-uat.yml`), i.e. exactly the `*.vercel.app` case that needs HSTS set by hand.
- **Concrete change:** add a `headers` block in `vercel.json` applied to `/(.*)`:
  `Strict-Transport-Security: max-age=63072000; includeSubDomains` (hold `preload` until JB confirms
  every subdomain is HTTPS-only — preload is hard to reverse), `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`,
  `Permissions-Policy: camera=(), microphone=(), geolocation=()`. Smoke the app + extension handoff
  + Supabase/Realtime calls, then **TRACK** a `Content-Security-Policy` as a follow-on (CSP needs an
  allowlist for Supabase, Vercel Analytics, and any LLM/Browserbase origins, and must be tuned so it
  doesn't break the SPA).
- **Sources:** [Security headers — Vercel Docs](https://vercel.com/docs/cdn-security/security-headers);
  [Response headers — Vercel Docs](https://vercel.com/docs/headers/response-headers);
  [Missing HSTS header on Vercel — SafeToShip](https://safetoship.dev/fix/missing-hsts/on/vercel);
  [OWASP Secure Headers Project](https://owasp.org/www-project-secure-headers/) (2026).
- **Recommended action: IMPLEMENT** the safe header subset (additive, reversible; HSTS **without**
  `preload`); **TRACK** CSP + HSTS-preload separately.

### S52 — Harden the base `playwright.config.ts` for CI (`forbidOnly` · `retries` · `trace` · `reporter` · `projects`)
- **What's new:** current Playwright CI guidance (2026) standardizes a small flag set:
  `forbidOnly: !!process.env.CI`, `retries: process.env.CI ? 2 : 0`, `trace: 'on-first-retry'`, an
  `html` (+ machine-readable) reporter, and explicit `projects` device(s).
- **Why it matters for bk-ai-apply:** the **non-UAT** base config (`playwright.config.ts`, which the
  `e2e` CI job runs) is barebones — only `testDir`, `baseURL`, `webServer`. It has **no
  `forbidOnly`** (a stray `test.only` silently narrows CI to one test and still ships green), **no
  `retries`/`trace`** (CI failures arrive with no replayable artifact), and **no
  `reporter`/`projects`**. The AI-UAT config (`playwright.uat.config.ts`) is already hardened
  (trace/video/reporters) — the **base config is the gap**, and it's the determinism/observability
  layer **under** S49's always-on e2e gate.
- **Concrete change:** add to `playwright.config.ts`: `forbidOnly: !!process.env.CI`,
  `retries: process.env.CI ? 2 : 0`, `workers: process.env.CI ? 1 : undefined`,
  `reporter: process.env.CI ? [['html', { open: 'never' }], ['list']] : 'list'`,
  `use.trace: 'on-first-retry'`, and `projects: [{ name: 'chromium', use: devices['Desktop Chrome'] }]`.
  Upload `playwright-report/` as a CI artifact (mirror `ai-uat.yml`). Pure config; no test changes.
- **Sources:** [Test configuration — Playwright Docs](https://playwright.dev/docs/test-configuration);
  [Trace viewer — Playwright Docs](https://playwright.dev/docs/trace-viewer-intro);
  [Playwright Test config options: complete reference — qaskills.sh](https://qaskills.sh/blog/playwright-test-config-options-complete-reference) (2026).
- **Recommended action: TRACK** — additive and safe, but best landed **with** S49 (the `retries`
