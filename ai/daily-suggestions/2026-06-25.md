### S25 — Wire the official Playwright MCP into the dev loop (deterministic a11y-tree browser tool)
- **What's new:** Microsoft's official **Playwright MCP** (`@playwright/mcp`,
  `microsoft/playwright-mcp`) drives a real browser for an agent off the **accessibility
  tree**, not screenshots — `browser_snapshot` returns a compact role/label/name
  structure (~200–400 tokens) instead of pixels or raw DOM. In 2026 it has become the
  default reference server of the agentic-Playwright ecosystem (40+ tools: navigate,
  forms, network mocking, storage, tracing).
- **Why it matters for bk-ai-apply:** the only MCP wired today is **Jam**
  (`.vscode/mcp.json`). The AI-UAT suite (`e2e/ai-uat/`) is driven by Stagehand +
  Browserbase — vision/LLM-based, non-deterministic (`retries: 0`), and metered. A
  deterministic, low-token browser MCP gives the Claude Code loop (and the `Qa-Uat`
  agent during interactive authoring) a fast, free way to navigate the running app,
  read structure, and draft/repair specs — complementary to the tracked Chrome DevTools
  MCP (S21, perf/trace) and Playwright Agents (S12).
- **Concrete change (narrow):** add a `playwright` server block to `.vscode/mcp.json`
  (`npx @playwright/mcp@latest`); optionally add it to the Claude Code MCP config used
  in your loop. Pilot by having an agent drive the Codespaces dev URL and produce one
  `e2e/ai-uat` spec scaffold. No app-code or dependency change.
- **Sources:** [Playwright MCP — Introduction (playwright.dev)](https://playwright.dev/docs/getting-started-mcp);
  [microsoft/playwright-mcp (GitHub)](https://github.com/microsoft/playwright-mcp);
  [Playwright Test Agents & MCP: 2026 Architecture Guide — TestQuality](https://testquality.com/playwright-test-agents-mcp-architecture-2026/) (2026).

### S26 — Adopt Supabase declarative schemas (generate migrations from desired-state files)
- **What's new:** Supabase's **declarative schema** workflow lets you keep the desired
  end-state of each table/policy in `supabase/schemas/*.sql` and run `supabase db diff`
  to **generate** the ordered migration. A June 2026 update made declarative sync handle
  the platform baseline automatically, so new declarative projects need less manual
  setup before their first apply.
- **Why it matters for bk-ai-apply:** the repo carries **30+ hand-written, timestamped
  migrations** under `supabase/migrations/` and **no `supabase/schemas/`**. For an
  event-sourced app whose non-negotiables hinge on RLS-always-on and per-`user_id`
  scoping, current-state schema files make RLS policies reviewable as one artifact
  (not reconstructed across 30 diffs) and reduce drift between what's declared and what's
  deployed. Distinct from per-PR preview DBs via Branching (S13) — this is the
  authoring/source-of-truth model, not the CI environment.
- **Concrete change:** pilot on one low-risk table — e.g. `user_settings`. Create
  `supabase/schemas/user_settings.sql` describing the desired state (table + RLS), then
  `supabase db diff -f user_settings_declarative` and confirm the generated migration is
  a no-op against current `main`. Document the diff-engine caveats (some objects still
  need manual migrations) in an ADR before converting more tables. Keep `pnpm db:gen-types`
  in the loop unchanged.
- **Sources:** [Declarative database schemas — Supabase Docs](https://supabase.com/docs/guides/local-development/declarative-database-schemas);
  [Supabase release notes / changelog — June 2026 (declarative sync baseline)](https://supabase.com/changelog).
- **Recommended action: TRACK** — migration-workflow change with known diff-engine
  caveats; pilot on one table + ADR before broader adoption (release safety first).

### S27 — Give the Orchestrator an explicit compaction + memory-tool discipline for long cycles
- **What's new:** Anthropic's context-engineering guidance for **long-horizon agents**
  centers on three techniques: **compaction** (summarize a near-full context window and
  reinitialize), **structured memory** (write context to files for cross-session reuse),
  and **sub-agent architectures**. Claude Code now keeps continuous session memory so
  compaction is near-instant, and **Memory for Managed Agents** (public beta, **Apr 23,
  2026**) formalizes cross-session, file-based, audited agent memory.
- **Why it matters for bk-ai-apply:** the dispatch contract threads a **persistent,
  growing `work_order`** through every phase (`AGENTS.md` → "context is threaded, not
  re-derived"), and `.claude/agent-memory/orchestrator/` already exists. Long release
  cycles (Wave 2/3 graphs span 6–7 agents) will approach context limits with no defined
  compaction point, risking silent context loss mid-cycle. A documented rule — compact
  the `work_order` to a summary + persist key decisions to `agent-memory` at defined
  checkpoints — hardens the loop. This is mechanistically distinct from S22 (parallel
  fan-out + `/rewind`): S27 is context-window management and cross-session persistence.
- **Concrete change:** add a "Context compaction & memory" block to
  `docs/conventions/agent-protocol.md`: when the threaded `work_order`/transcript nears
  the window, the Orchestrator emits a compacted `work_order` summary and writes
  durable decisions to `.claude/agent-memory/orchestrator/`. Prototype on one
  `wave2-dry-run.prompt.md` pass and capture a lesson before amending agent contracts.
- **Sources:** [Effective context engineering for AI agents — Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents);
  [Scaling Managed Agents / Memory for Managed Agents — Anthropic](https://www.anthropic.com/engineering/managed-agents) (Apr 2026);
  [Manage context — Claude Code docs](https://docs.claude.com/en/docs/claude-code/costs).
- **Recommended action: TRACK** — touches the orchestration contract (agent integrity is
  first-class); prototype + lesson-capture before adopting.

### S28 — Audit the `.agents/skills/` library to the current Agent Skills authoring spec
- **What's new:** Anthropic's **Agent Skills** best practices make **progressive
  disclosure** the core principle: a skill's `name`+`description` frontmatter is the only
  thing always in context (it drives triggering), the `SKILL.md` body should stay **under
  ~500 lines**, and anything longer should be split into referenced files loaded on
  demand. Guidance is explicitly **evaluation-first** (build/trim skills against observed
  gaps).
- **Why it matters for bk-ai-apply:** the repo ships **21 skills (8,585 total lines)**,
  and **6 exceed the 500-line guidance** — `imagegen-frontend-mobile` (1,465),
  `image-to-code` (1,228), `design-taste-frontend-v2` (1,206), `imagegen-frontend-web`
  (987), `brandkit` (798), `emil-design-eng` (679). The Orchestrator's UI dispatch policy
  *mandates* reading `design-taste-frontend` + `emil-design-eng` on every UI phase, so
  oversized bodies are loaded into specialist context on a hot path — burning tokens and
  diluting triggering precision. Distinct from the AGENTS.md/context-file audit (S08);
  this targets the skills library specifically.
- **Concrete change:** start with the worst hot-path offender, `emil-design-eng` (679
  lines, loaded on every UI phase): split the `SKILL.md` body to <500 lines and move
  detailed references into adjacent files the skill points to (progressive disclosure);
  verify triggering/behavior is unchanged on one `wave2-dry-run` UI pass. Then queue the
  four `imagegen*`/`image-to-code` skills. Tighten `description` fields where triggering
  is ambiguous.
- **Sources:** [Equipping agents for the real world with Agent Skills — Anthropic Engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills);
  [Skill authoring best practices — Claude Docs](https://docs.claude.com/en/docs/agents-and-tools/agent-skills/best-practices).
- **Recommended action: TRACK** — verified gap (6 skills over the limit) but the fix is
  multi-file rewrites; pilot on `emil-design-eng` first, measure, then expand.

### S29 — Add an agent-readable `llms.txt` index of the project's canonical context
- **What's new:** `llms.txt` is, by 2026, the first widely-adopted **Business-to-Agent**
  convention — a curated Markdown index of an artifact's highest-value docs that IDE
  agents (**Claude Code, Cursor, Copilot, Cline, Aider**) look for and fetch. Anthropic's
  and Vercel's own docs were early adopters. (It remains a community convention, not a
  W3C/IETF standard.)
- **Why it matters for bk-ai-apply:** the repo has deep `/docs` (architecture, domain
  rules, ADRs, conventions, requirements) but **no curated entry index** — `docs/README.md`
  does not exist, and the human KB-index idea (S10) is still open. A root `llms.txt`
  giving an agent a one-screen map of the canonical context (CLAUDE.md, AGENTS.md,
  `docs/architecture.md`, `docs/domain/business-rules.md`, `docs/conventions/`,
  `docs/adr/`) shortens every agent's Pre-Flight Reads and centralizes "where the truth
  lives." It's the agent-facing complement to S10's human index — additive and zero-risk.
- **Concrete change:** add `llms.txt` at repo root: a short title/blurb plus a linked,
  one-line-described list of the canonical docs above. Keep it hand-curated (don't dump
  everything). Optionally add `llms-full.txt` later if/when docs are ever published.
- **Sources:** [llms.txt proposal — llmstxt.org](https://llmstxt.org/);
  [The State of llms.txt in 2026 (adoption across Claude Code/Cursor/Copilot/Cline/Aider)](https://presenc.ai/research/state-of-llms-txt-2026).
- **Recommended action: IMPLEMENT** — single additive root file, no behavior change,
  fills a verified gap (no `llms.txt`, no `docs/README.md`). Pairs with the still-open S10.
