## Suggestion cards

### 1. Raise the unattended security floor to `>=2.1.277` — four more permission-checker bypasses  [Recommend: IMPLEMENT]

**What's new.** Four releases since S209 set the floor at 2.1.260 each fixed a way a Bash command could slip past the permission checker:

- **2.1.271** — five at once: permission checks missed the file that `fmt`/`column` read when it followed an unrecognized option; skipped files a wildcard expands to when the wildcard sits in an option value (`grep -v dir/* file`); **shell variable declaration flags could misrepresent the command being run**; and commands with two directory changes, a subshell, or a `cd`+`git` chain **skipped the prompt under `permissions.blockReadsOutsideWorkingDirectories` in bypass and auto mode**.
- **2.1.273** — commands the checker cannot fully analyze skipped the prompt under the same setting, and **a subshell could hide a dangerous `rm` in bypass mode**.
- **2.1.274** — commands that loop over or assign certain special shell variables now ask for permission; worktree-isolated sessions now refuse certain nested shell expansions.
- **2.1.277** — a `sandbox.excludedCommands` glob **exempted an entire compound Bash command from the sandbox when only one part matched**; every part must now match.

**Why it matters for bk-ai-apply.** The declaration-flag fix in 2.1.271 and the special-variable fix in 2.1.274 are the **fourth and fifth** instances of assignment-smuggling in this ledger (S115, S201, S209). That is now a pattern, not a run of bad luck: the Bash permission checker is a parser, and parsers lose to shell grammar repeatedly. The `sandbox.excludedCommands` compound-command bug is the more alarming one for this repo specifically — it means a single matching fragment could carry a whole `&&` chain out of the sandbox, which is the exact shape of the commands a `/loop` iteration runs (`cd x && pnpm validate && git status`).

**Concrete change.** Set `requiredMinimumVersion` to `2.1.277` in `.claude/settings.json` (the same still-queued settings commit as S201/S203/S209/S213/S219). Running target `>=2.1.278`. Supersedes the S209 floor of 2.1.260. While in that file, audit any `sandbox.excludedCommands` entries for globs that would have matched only one leg of a compound command.

**Sources.** Claude Code changelog 2.1.271, 2.1.273, 2.1.274, 2.1.277.

### 2. Per-command `allowed_domains` — the fix for "an allowlist is a capability grant"  [Recommend: IMPLEMENT]

**What's new.** CC **2.1.271** added per-command `allowed_domains` to Bash, PowerShell and Monitor **in auto mode with sandboxing**: the hosts a command needs are reviewed *with that command* and opened **for it alone**; other hosts are refused.

**Why it matters for bk-ai-apply.** This is the direct structural answer to S225, the most consequential finding in this ledger. S225's point was that a session-wide egress allowlist is a *capability grant*, not a destination filter — allowlisting `api.supabase.co` for the whole session means any command in that session can reach it, including one steered by a poisoned file. Per-command scoping collapses the grant from session-lifetime to one reviewed command. It narrows S98 (`strictAllowlist`) and S110 (`setDomainPolicy`) from a standing grant to a per-use one, and it is the first change that moves the S225 numbers (~17% of overeager actions getting through auto mode) rather than just documenting them.

**Concrete change.** Requires auto mode **with sandboxing** — so it stacks on the S44/S98/S103/S125 sandbox line rather than replacing it. For the scheduled routine, the practical move is to stop granting `*.supabase.co` and `*.vercel.app` session-wide and attach them to the specific commands that need them (the Supabase CLI calls, the AI-UAT preview probe). Pair with S202 `--restricted` for the read-only research leg, which needs no egress at all. Record the reasoning in the same ADR that S225 was going to feed.

**Sources.** Claude Code changelog 2.1.271; Anthropic, "How we contain Claude across products" (May 25 2026) for the threat model this addresses.

### 3. `TaskOutput` tool and `taskOutputMaxChars` are gone — **S212 is now wrong**  [Recommend: TRACK]

**What's new.** CC **2.1.277**: *"Removed the deprecated TaskOutput tool; Claude reads a background task's output file with Read instead, and the `taskOutputMaxChars` setting and `TASK_MAX_OUTPUT_LENGTH` no longer have any effect."*

**Why it matters for bk-ai-apply.** S212 (Sep 8) recommended raising `bashOutputMaxChars`/`taskOutputMaxChars` to keep `pnpm validate` and `playwright test:uat` output inline instead of spilling to a file — the argument being that an unattended loop skips the extra read-the-file step. Half of that recommendation is now a no-op, and the half that remains has been **inverted by design**: reading a background task's output file with `Read` is the supported path now, not a failure mode to tune around. Do not put `taskOutputMaxChars` in the settings commit.

**Concrete change.** Drop `taskOutputMaxChars` from the queued S212 settings work; keep `bashOutputMaxChars` (still live, foreground Bash). Anywhere a `/loop` or `/dispatch` prompt tells the agent to expect inline task output, change it to instruct an explicit `Read` of the output file — and set that expectation in the command definition rather than relying on a limit.

**Sources.** Claude Code changelog 2.1.277.

### 4. Subagent results are now framed as subagent output — a real trust boundary for `/dispatch`  [Recommend: TRACK]

**What's new.** CC **2.1.277** changed subagent results to reach the main agent **under a header marking them as subagent output, with the result indented, so text in a subagent's result cannot pass as the session's own instructions**. The same release did the equivalent for workflow scripts' computed `agent()` prompts on Bedrock/Vertex/Foundry (framed as script-authored text so the safety classifier does not read them as the user). **2.1.271** separately added **`omitClaudeMd`** to agent frontmatter and `--agents` JSON, letting custom and plugin subagents run without user/project/local CLAUDE.md (managed policy files still load).

**Why it matters for bk-ai-apply.** S225 named multi-agent trust escalation — a subagent's output being treated as higher-trust than it is — as a live injection vector, and S193 found conflicting-directive sabotage in exactly this seam. Until now the `/dispatch` roster's defence was prompt discipline. This is the platform enforcing it: a worker agent that reads a poisoned file and echoes an instruction back can no longer have that instruction read as JB's. `omitClaudeMd` is the complementary knob on the way in — a narrow read-only leg (business-analyst, context-keeper, critical-path) does not need the repo's full non-negotiables in its prompt, and a smaller prompt is a smaller injection surface as well as cheaper.

**Concrete change.** Nothing to configure for the result-framing — it is automatic on `>=2.1.277`, which is another reason for card 1. For `omitClaudeMd`: add it to the frontmatter of the **read-only** roster agents only. Do **not** add it to `feature-dev`, `supabase-security` or `release-gate` — those need the non-negotiables. Record which agents carry it, and why, next to the S46 roster-drift notes.

**Sources.** Claude Code changelog 2.1.277, 2.1.271.

### 5. Unattended fail-loud cluster — and the most specific candidate fix yet for the GitHub connector  [Recommend: IMPLEMENT]

**What's new.** Three independent items:

- **2.1.277** — *"Fixed `claude -p` and Agent SDK sessions that could hang with no result after an internal error; they now report the error and exit with code 1."*
- **2.1.274** — added **`CLAUDE_CODE_MCP_STARTUP_WAIT_MS`** to bound how long the first non-interactive turn waits for connecting MCP servers (`0` = don't wait). Same release: MCP servers configured as `http` that only speak legacy HTTP+SSE no longer fail when the first request answers 422 or another 4xx; 403 `insufficient_scope` now names the missing permissions instead of claiming an expired sign-in.
- **2.1.271** — *"Fixed MCP OAuth mishandling client registrations: denying consent forced a new one, one for another redirect URI was reused, and a concurrent write could delete a valid one or keep a mismatched one."*

**Why it matters for bk-ai-apply.** The `-p` hang fix is the single most valuable line here for a scheduled routine. A hang and a slow run are indistinguishable in an unattended transcript; an exit code 1 is not. This is the upstream companion to S213's silent-no-output `/schedule` bug and S210's fail-closed `--permission-prompts none`, and it completes that set: prompts auto-deny, internal errors now exit loud. `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` is the direct mitigation for *this routine's* recurring cost — eight runs have opened by waiting on a GitHub MCP server that was never going to connect.

On the connector itself: the 2.1.271 OAuth **client-registration** fix is a closer match to `does not support dynamic client registration` than S224's 2.1.265 change (which stopped *eagerly* registering) or S205's 401-loop fixes. The concurrent-write leg — *"a concurrent write could delete a valid one or keep a mismatched one"* — is a plausible fit for a host running several Codespaces sessions against one `~/.claude.json` (S164, S210). Not a guarantee; a real candidate.

**Concrete change.** Set `CLAUDE_CODE_MCP_STARTUP_WAIT_MS` in the scheduled-task environment — a small non-zero bound, not `0`, so a healthy connector still attaches. Retry the GitHub connector on a CLI at `>=2.1.277` (card 1 gets you there anyway) and capture `mcp_server_errors` if it still fails. Unblock order is unchanged: S209 → S210 → S213 → S203 → S211, then S216 / S111.

**Sources.** Claude Code changelog 2.1.277, 2.1.274, 2.1.271.

### 7. Auto mode's classifier moved server-side and stopped billing for its own overhead  [Recommend: TRACK]

**What's new.** CC **2.1.278** changed auto mode for Claude API and Enterprise users, and on Bedrock/Vertex/Foundry/gateways, to **default to the server-side classifier, which does not charge for classifier overhead** (`CLAUDE_CODE_AUTO_MODE_SERVER=0` opts out on the platform providers); it warns on billed fallback. The same release added an **`Auto mode server` row to `/status`** showing whether this session's classifier runs on the server. This reverses the 2.1.273 change that put Bedrock/Vertex/Foundry back on the *local* classifier by default.

**Why it matters for bk-ai-apply.** The unattended cost line (S181 budget headroom, S203 Loops breakdown, S222 `maxEffortLevel`) has never accounted for classifier overhead as a separate charge, because it was invisible. It is now both cheaper and *observable* — and the "warns on billed fallback" behaviour means a silent regression back to the paid path announces itself. That matters because the default here has already flipped twice in five releases.

**Concrete change.** No setting to add for a first-party subscription. Do add a `/status` check to the routine's own opening steps, so the `Auto mode server` row is recorded in each run's transcript — it makes a cost jump attributable rather than mysterious. Re-baseline the S181 budget headroom after one week on `>=2.1.278`.

**Sources.** Claude Code changelog 2.1.278 and 2.1.273; [Auto mode classifier billing — Claude Code Docs](https://code.claude.com/docs/en/auto-mode-classifier-billing).

### 8. Supabase Advisors now cover **Health** — an agent-readable catalyst signal  [Recommend: IMPLEMENT]

**What's new.** **Sep 18, 2026**: Supabase Advisors added a **Health** category alongside Security and Performance. v1 ships four service error-rate checks read from log data — `log_data_api_error_rate_high` (PostgREST 5xx), `log_auth_error_rate_high`, `log_storage_error_rate_high`, `log_edge_function_error_rate_high` — surfaced in a Studio **Advisors → Health** tab and via `POST /v2/projects/{ref}/advisors/run`, which returns health results alongside security and performance. Supabase describe them as *"particularly useful as a signal source for agents — an elevated rate check is a reliable catalyst for automated investigation flows."* Crucially, **an empty result means all checks ran and found nothing, while `advisor_check_unavailable` means a check could not run** — healthy and unchecked are distinguishable. Database connectivity probes and instance health checks are on the roadmap.

**Why it matters for bk-ai-apply.** This fills a genuine, verified gap: the mirror's `.github/workflows/ai-uat.yml` and `ci.yml` have no Supabase-side health gate, and nothing in the ledger proposes one. Today an AI-UAT run against a preview with an unhealthy Auth or Edge Functions service produces a pile of confusing UI failures — the pipeline board is blank, and the evaluator has no way to tell "RLS denied it" from "PostgREST is 5xx-ing" (the precise confusion S208 described). One API call before the suite turns that into a known-bad precondition. The healthy-vs-unchecked distinction is what makes it safe to gate on: most health endpoints fail open and quietly.

**Concrete change.** Add a pre-flight step to `.github/workflows/ai-uat.yml` that calls `POST /v2/projects/{ref}/advisors/run` and **fails the job fast** on an elevated error-rate check, rather than spending the full UAT budget. Treat `advisor_check_unavailable` as a warning, not a failure. Persist the response as a CI artifact next to the run so the evaluator has the precondition on record. The same call is available in-session via the Supabase MCP `get_advisors` tool, which makes it cheap for `/loop` to check before declaring a failure a code failure. Results are cached server-side, so polling is not punished.

**Watch.** Health checks are **read from log data** — verify their behaviour across the `logs.all` → `logs` endpoint migration landing **2026-09-23, two days from now** (S218/S226).

**Sources.** [Supabase changelog — Advisors: Health checks (Sep 18, 2026)](https://supabase.com/changelog).
