### 2. S132 — Anthropic **"Harness design for long-running application development"** (planner → generator → evaluator; evaluator drives the live app via Playwright MCP): adopt as the architecture for `/dispatch` + the AI-UAT evaluator — **[Recommend: IMPLEMENT]** *(design spec; repo write gated on GitHub)*
- **What's new (to this ledger):** A distinct, more advanced successor to S130's Nov-2025 "Effective harnesses" post. Prithvi Rajasekaran (Anthropic Labs) documents a **GAN-inspired multi-agent harness**: a **planner** expands a 1–4 sentence prompt into an ambitious, deliberately high-level product spec; a **generator** implements one feature/sprint at a time on a **React + Vite + FastAPI + SQLite→PostgreSQL** stack with git discipline; and a separately-tuned, **skeptical evaluator** uses the **Playwright MCP to click through the running app** (UI + API endpoints + DB state) the way a user would, filing concrete bugs and grading each sprint against hard-threshold criteria (product depth, functionality, visual design, code quality). Before each sprint the generator and evaluator negotiate a **"sprint contract"** (what "done" means + the testable behaviors) via file-based handoff. Key documented lessons: **separate the doer from the judge** (self-evaluation reliably skews positive), **context resets > compaction** for "context anxiety" on weaker models, and **strip harness scaffolding as the model improves** (they dropped context resets and the sprint construct on Opus 4.6, keeping only planner + a single end-of-run evaluator when the task sits within the model's solo capability).
- **Why it matters for bk-ai-apply:** This maps almost 1:1 onto the two open themes at once. **(Theme 2 / S06):** planner→generator→evaluator is the concrete shape for `/dispatch` waves and the `/loop` skeleton, extending the piecemeal primitives already tracked (S07 Dynamic Workflows, S22 fan-out+checkpoint, S27 compaction, S38 Agent Teams, S130 harness skeleton). **(Theme 1 / autonomous UAT):** the **evaluator-with-Playwright-MCP grading a running app against hard-threshold contracts** IS the autonomous-UAT gate this project has been building toward (S01/S12/S19/S25/S30) — but expressed as an *agentic judge* rather than only static assertions. The stack in the post (React+Vite+Postgres) is this repo's stack. The "sprint contract + hard threshold or the sprint fails" rule is the enforcement mechanism the repo's "validate before done" non-negotiable wants.
- **Concrete change (narrow; when S06 is authored — no repo write today):**
  - Structure `.claude/commands/dispatch.md` as **planner → generator → evaluator** personas with **file-based handoff** under `ai/loop/` (contract file per feature, flip-only feature list per S130).
  - Give the **evaluator persona the Playwright MCP** (register via the tracked S32 `.mcp.json`; version-locked Playwright MCP per S108) and require it to exercise the running preview and grade against per-feature **hard-threshold contracts** before any feature is marked done — the agentic tier above the deterministic gates (S19/S30).
  - Encode "**doer ≠ judge**" and "**strip scaffolding as the model improves**" as explicit notes in the S06 spec; re-baseline the persona models on the current default (ties to S97/ADR-010).
  - Keep it a **design note folded into the S06 spec** for now.

### 4. S134 — Supabase **breaking change: the `realtime` schema is now fully locked down against modifications** — add a migration CI-guard heads-up — **[Recommend: TRACK]**
- **What's new:** Supabase now **blocks all changes to the `realtime` schema** — creating, altering, or dropping objects fails with a permission error. **RLS policies on `realtime.messages` still work.** (Breaking change, published **Jul 14 2026**; never surfaced in this ledger.)
- **Why it matters for bk-ai-apply:** The app **uses Realtime** (client `.channel()`/`postgres_changes` in 2 `src/` files, per CLAUDE.md's "Auth + Realtime" stack) and ships **34 SQL migrations**. **Good news, verified today:** none of the current migrations issue DDL against the `realtime` schema, so **nothing is broken now**. The risk is *future*: any migration that tries to `CREATE`/`ALTER`/`DROP` inside `realtime.*` (e.g. hand-adding a publication/trigger there) will now hard-fail on `supabase db push` and in per-PR branch DBs. This is the same class of platform heads-up as S118 (extension-version pinning) and S47 (Data-API exposure).
- **Concrete change (narrow, doc + optional guard):**
  - Add a one-line note to `docs/domain/data-model.md` (or `business-rules.md`): *"Never author DDL against the `realtime` schema — it is locked; use RLS on `realtime.messages` instead."*
  - Optional cheap CI guard: fail `ci.yml` if any file under `supabase/migrations/` matches `(create|alter|drop)\b.*\brealtime\.` — catches the mistake before it reaches a branch DB.
- **Source(s):** [Supabase changelog — "Realtime schema is now fully locked down against modifications"](https://supabase.com/changelog/realtime-schema-locked-down-against-modification) (Breaking Change, Jul 14 2026).
