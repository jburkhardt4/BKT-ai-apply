## Suggestions

### S19 — Deterministic ARIA-snapshot assertions in the AI-UAT suite
- **What's new:** Playwright's `expect(locator).toMatchAriaSnapshot()` compares the
  rendered accessibility tree (YAML) instead of pixels; recent releases let snapshots
  live in separate `.aria.yml` files, work on `page`, and emit element bounding boxes
  (`boxes`) specifically "useful for AI consumption."
- **Why it matters for bk-ai-apply:** `playwright.uat.config.ts` sets `retries: 0`
  because "AI agents are non-deterministic." Today the AI-UAT specs capture
  `screenshot: 'on'` but assert **nothing** about structure — the Stagehand agent can
  silently drift and a run still passes. ARIA snapshots add a deterministic structural
  gate that is independent of the LLM's path, without the flakiness of pixel diffs
  (the pending S01). Playwright is already pinned at `1.60.0`, so the API ships today —
  no upgrade, no new dependency.
- **Concrete change (narrow):** In `e2e/ai-uat/smoke.spec.ts` and the per-feature
  specs (`pipeline`, `auth`, `job-fit`), after the agent reaches each key surface, add
  `await expect(page).toMatchAriaSnapshot({ name: '<surface>.aria.yml' })`. Generate
  baselines once with `pnpm test:uat --update-snapshots`; commit the `.aria.yml` files.
  Optionally extend `validate`/CI to run the snapshot-only subset (fast, deterministic).
- **Sources:** [Snapshot testing — Playwright](https://playwright.dev/docs/aria-snapshots);
  [Playwright release notes](https://playwright.dev/docs/release-notes) (ARIA-snapshot
  enhancements through 2025; feature GA since v1.49, Dec 2024).
- **Recommended action: IMPLEMENT** — fills a verified gap (AI-UAT asserts no structure;
  no aria/snapshot usage anywhere in repo), tiny scope, no new deps.

### S20 — Vitest 4 Browser Mode + `toMatchScreenshot` for component-level visual regression
- **What's new:** Vitest 4.0 (released 2025-10-22) graduated **Browser Mode** to stable
  and added **built-in visual regression** via `toMatchScreenshot`, plus first-class
  Playwright trace capture for component tests.
- **Why it matters for bk-ai-apply:** `package.json` already has `vitest@^4.1.8`, but
  `vite.config.ts` runs unit tests in the default (jsdom-style) environment with no
  browser project and no component visual coverage. Browser Mode tests shadcn/Radix +
  Tailwind v4 components in a real engine — catching render/state regressions at the
  component layer, a tier below the e2e pixel-diff idea (S01) and the agent-level UAT.
- **Concrete change:** Add a `test.browser` block (provider: `playwright`,
  `instances: [{ browser: 'chromium' }]`) to `vite.config.ts` or a dedicated
  `vitest.browser.config.ts`; add a `test:component` script; start with one
  `*.browser.test.tsx` on a high-traffic component (e.g. pipeline card) using
  `await expect(el).toMatchScreenshot()`. Gate later once baselines are stable.
- **Sources:** [Vitest 4.0 announcement — VoidZero](https://voidzero.dev/posts/announcing-vitest-4)
  (2025-10-22); [Vitest 4.0 blog](https://vitest.dev/blog/vitest-4);
  [InfoQ: Vitest 4 Browser Mode & visual regression](https://www.infoq.com/news/2025/12/vitest-4-browser-mode/) (2025-12).
- **Recommended action: TRACK** — genuine new capability on a tool you already own;
  sequence it against the still-pending S01 so you don't stand up two overlapping
  visual-regression stacks at once.

### S22 — Parallel subagent fan-out + checkpoint/rewind for the dispatch loop
- **What's new:** Current Claude Code guidance treats the main session as an orchestrator
  that **fans out independent work to subagents in parallel** (bounded changesets, tight
  scope) and uses **checkpoints / `/rewind`** to snapshot and restore state at each step
  — patterns formalized in the 2026 subagent best-practices material.
- **Why it matters for bk-ai-apply:** `docs/conventions/agent-protocol.md` and
  `.claude/agents/orchestrator.md` define a **sequential, phase-gated** dispatch with a
  single retry. Independent specialists (e.g. `Ui-Ux` on a new surface and
  `Supabase-Security` on an RLS policy) are serialized even when they don't conflict.
  Documenting an explicit parallel-vs-sequential rule, plus checkpoint-before-dispatch,
  would shorten cycles and make the "retry once" semantics resumable — while keeping
  your phase gates intact.
- **Concrete change:** Add a "Parallelization & checkpoints" block to
  `docs/conventions/agent-protocol.md`: when phase subtasks touch disjoint file sets,
  the Orchestrator dispatches them concurrently and merges packets at the gate; checkpoint
  before each dispatch so a failed gate rewinds cleanly. Prototype on one feature wave
  (`wave1-dry-run.prompt.md`) and capture a lesson before changing agent contracts.
- **Sources:** [Best practices for Claude Code (official docs)](https://code.claude.com/docs/en/best-practices);
  [Claude Code Agent Teams & Subagents — 2026 Playbook](https://www.developersdigest.tech/blog/claude-code-agent-teams-subagents-2026) (2026).
- **Recommended action: TRACK** — touches the orchestration contract (agent integrity is
  first-class); prototype + lesson-capture before adopting.

### S23 — Single lockfile + `packageManager` pinning (remove stray `package-lock.json`)
- **What's new:** Standard guidance for pnpm repos: commit **only** `pnpm-lock.yaml`,
  never a second package manager's lockfile, and pin the manager via the
  `packageManager` field (Corepack) so local and CI resolve identically.
- **Why it matters for bk-ai-apply:** the repo ships **both** `pnpm-lock.yaml` **and**
  `package-lock.json`, and `package.json` has **no** `packageManager` field. CI runs
  `pnpm install --frozen-lockfile` (Node 22 / pnpm 10), so the npm lockfile is dead
  weight that will silently drift and invites a contributor to `npm install` into an
  inconsistent tree. This is release-safety hygiene, distinct from the pending
  `.devcontainer` toolchain pin (S09) and gh-aw action-SHA pinning (S16).
- **Concrete change:** `git rm package-lock.json`; add `echo 'package-lock.json' >> .gitignore`;
  add `"packageManager": "pnpm@10.x"` to `package.json` (match the CI `pnpm/action-setup`
  version). Re-run `pnpm install --frozen-lockfile` to confirm clean. No app code touched.
- **Sources:** [pnpm and package-lock.json — DEV](https://dev.to/drarig29/pnpm-and-package-lock-json-2d05);
  [Vercel: Package Managers](https://vercel.com/docs/package-managers);
  [The packageManager field & Corepack](https://blog.hyperknot.com/p/corepacks-packagemanager-field).
- **Recommended action: IMPLEMENT** — verified gap, narrow scope, improves release
  reproducibility; no secrets/auth/CI-credential changes.

### S24 — GitHub Codespaces prebuilds on top of a devcontainer
- **What's new:** Codespaces **prebuilds** run the full devcontainer setup ahead of time
  and store the result, so new/rebuilt codespaces skip install + build. GitHub notes
  repos that take >2 min to spin up benefit materially.
- **Why it matters for bk-ai-apply:** Codespaces is the primary dev environment, but
  there's no `.devcontainer/` yet (the pending S09). Once S09 lands, a prebuild config
  (triggered on push to `main` + on devcontainer changes) would make Codespace startup
  near-instant for you and any future contributor — directly improving the
  "Codespace/repo setup" theme. This is the speed/caching layer that sits on top of S09's
  toolchain pin, not a duplicate of it.
- **Concrete change:** After S09 adds `.devcontainer/devcontainer.json`, move slow steps
  into `onCreateCommand`/`updateContentCommand` (e.g. `pnpm install`,
  `pnpm exec playwright install --with-deps chromium`), then enable a prebuild for `main`
  via Settings → Codespaces → Set up prebuild.
- **Sources:** [About GitHub Codespaces prebuilds](https://docs.github.com/en/codespaces/prebuilding-your-codespaces/about-github-codespaces-prebuilds);
  [Configuring prebuilds](https://docs.github.com/en/codespaces/prebuilding-your-codespaces/configuring-prebuilds).
