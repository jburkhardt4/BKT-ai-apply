## 1. [Recommend: IMPLEMENT] CC 2.1.260 file-permission security cluster — raise unattended CLI floor to >=2.1.260

**What's new** — 2.1.260 (Sep 3) fixes three defects in the *permission-rule evaluator itself*, not in what it guards. 2.1.261 (Sep 4) and 2.1.263 (Sep 6) follow with features and fixes only.

**Why it matters for bk-ai-apply** — Every sandbox card since S44 assumes a deny rule that parses is a deny rule that holds. These break that assumption in both directions:
- **`Edit`/`Write`/`Read` rules whose path contains parentheses were dropped as invalid or ignored by the Bash sandbox — leaving "read-only" folders writable.** A silent fail-*open*. Repo paths with parentheses are plausible in `docs/` and any Windows-side path.
- **One rule with an uncompilable pattern (e.g. an unclosed `[`) made *every* file edit fail** with `Invalid regular expression`. A fail-*closed* that would read in an unattended transcript as an unrelated tool bug; such a deny rule now guards the literal path it spells.
- **Bash checks auto-approved zsh commands hiding a command substitution in a `REPORTTIME` / `REPORTMEMORY` / `DIRSTACKSIZE` assignment.** Same family as the 2.1.221 `$PSDefaultParameterValues` bypass (S115) and the 2.1.251 arithmetic-assignment bypass (S201) — third instance of "assignment syntax smuggles execution past auto mode."
- `permissions.blockReadsOutsideWorkingDirectories` on macOS was **hiding a worktree-isolated sub-agent's own checkout** — directly hits the S119/S202 worktree-isolation design.
- **Reverted** the 2.1.259 change applying `Read()` deny rules to Bash arguments: it denied `npm run build` under a `Read(./**/build/**)` rule *in every mode*. If you had drafted S201-era deny globs against `build/`, they were briefly load-bearing in the wrong direction.
- Also: rules with text after the closing paren (`Bash(ls) x`) now **report as invalid settings** instead of being silently ignored — worth a `claude doctor` pass on any hand-written rule.

**Concrete change** (narrow)
1. `.claude/settings.json` — `requiredMinimumVersion: "2.1.260"` (S104 mechanism). Supersedes the S201 floor of 2.1.251. Running target `>=2.1.263`.
2. Bump the CLI in the scheduled-task env and in Codespaces; run `claude doctor` and read the new "Organization policy" line (2.1.261) if policy load is silently failing behind a proxy.
3. Grep every `Edit(...)` / `Write(...)` / `Read(...)` rule for parentheses and unbalanced brackets before assuming the S201 rule set is enforced. 2.1.261 improves the settings error for `Edit(C:\dir\(name)\**)` specifically — a Windows-path shape JB will hit.

## 2. [Recommend: IMPLEMENT] CC 2.1.259 `--permission-prompts none` — the missing determinism primitive for the scheduled routine

**What's new** — 2.1.259 (Sep 2) added `--permission-prompts none` "for unattended headless hosts: anything that would prompt is denied automatically while the active permission mode (including auto mode) keeps deciding."

**Why it matters for bk-ai-apply** — This is the primitive S82/S157/S161 have been approximating with policy. Every unattended-safety card so far either *confines* execution (sandbox line S44/S98/S103/S125), *removes* it (S202 `--restricted`), or *configures a default mode* and hopes nothing prompts. None of them answer "what happens when something prompts anyway at 07:14 with nobody there." Until now the answer was: the run blocks, or a changed default (S157) silently decides for you. `--permission-prompts none` makes the answer explicit and fail-closed **without** disabling auto mode's classifier — so the loop still proceeds on everything auto mode can decide, and only genuinely novel requests die.

The pairing that makes it operational: 2.1.260 also fixed `-p --resume`/`--continue` failing on every retry once a session's worktree lost its git metadata, and 2.1.259 fixed **concurrent sessions silently reverting each other's `~/.claude.json`** — workspace trust no longer resets and MCP/project state is no longer lost when many sessions run at once. JB runs multiple Codespaces (S164); that bug is a plausible contributor to the recurring MCP-state weirdness.

**Concrete change**
1. Add `--permission-prompts none` to the scheduled-task invocation and to any `claude -p` leg of `/loop` and `/dispatch`.
2. Decide and record the interaction with S157 (auto mode as the new default) and S161 (auto-continue at usage-limit reset) in the same ADR — all three now govern what an unattended run does when it hits an edge.
3. Do **not** combine with `bypassPermissions`; the point is a deterministic deny floor.

**Source** — Claude Code changelog, 2.1.259 (Sep 2 2026): https://code.claude.com/docs/en/changelog

**Advances** S82/S157/S161/S202.

## 9. [Recommend: TRACK] pnpm 12.0 Rust rewrite (Aug 26) → 12.4.0 — changes the still-open S23 `packageManager` decision

**What's new** — pnpm **12.0** shipped **2026-08-26**: a rewrite from TypeScript to Rust, distributed as **native per-platform binaries with no Node.js launcher**. Point releases have moved fast — 12.2.1 (Sep 1) through **12.4.0 (Sep 8)**, six releases in eight days — and an **11.26.0** backport landed Sep 6, so the 11.x line is still maintained. Breaking changes are narrow and correctness-oriented: deterministic peer-cycle cutting, lockfile bytes now depending only on the dependency graph (reordering workspace projects or installing twice produces identical bytes), git dependencies on known hosts treated as identity rather than transport, and `pnpm self-update` no longer honoring project-level `.npmrc` / `pnpm-workspace.yaml` / `.pnpmfile`.

**Why it matters for bk-ai-apply** — S23 (single lockfile + `packageManager`/Corepack pin, still open — the mirror confirms **both** `package-lock.json` and `pnpm-lock.yaml` present and **no `packageManager` field**) and S196 (pnpm 11.23 frozen-install failure on a bumped pin without lockfile regen) were both designed against a **Node-launched, Corepack-managed** pnpm. A native binary with no Node launcher changes what "pin the package manager" even means — Corepack's model is downloading and running a Node package. Deciding S23 now, on 11.x semantics, risks writing a pin that has to be redone. The deterministic-lockfile change is a genuine win for CI cache keys and for reviewing `/loop`-generated diffs, where a spurious lockfile reorder is noise an agent will happily commit.

**Recommended action is to wait.** Six releases in eight days on a fresh Rust rewrite is not a floor to pin production CI to, and JB's stated preference is release safety over experimentation. Let 12.x settle, then decide S23 once — against 12.x semantics and with the Corepack question answered.

**Concrete change** — none today. Amend the S23 backlog line: "blocked pending pnpm 12.x stabilization; re-evaluate the Corepack/`packageManager` mechanism against native binaries before writing the pin."
