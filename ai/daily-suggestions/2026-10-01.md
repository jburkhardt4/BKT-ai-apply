## 5. Postgres 15.19 / 17.11 — Breaking Change, 44 CVEs, upgrade live since Sep 28
**[Recommend: IMPLEMENT]** — human decision gate, Tier 2/Tier 3

**What's new.** Supabase, 2026-09-25, tagged **Breaking Change**: "We are rolling out the PostgreSQL
**15.19 / 17.11** minor release (from 15.14 / 17.6). It bundles five upstream security cycles and
closes **44 CVEs**" — several rated High. Four changes may require action:
1. **ltree** indexes may need reindexing — a case-folding fix affecting multibyte/ICU or non-`libc`
   collation-provider databases, where indexes "can silently return incomplete results"; plus an
   integer-overflow fix where "values with more than about 14,653 labels could compare incorrectly,
   which can corrupt B-tree indexes".
2. **pgcrypto** "stops decrypting legacy-cipher PGP data (CVE-2026-14663) — data encrypted with
   `cipher-algo=bf`/`blowfish`/`cast5` was effectively stored unencrypted and fails to decrypt by
   default after the upgrade." Recoverable with `ignore-cipher-failure=1`, "and the underlying data
   remains effectively unencrypted at rest until re-encrypted."
3. **btree_gist** indexes on `float4`/`float8` columns that may contain `NaN` need reindexing.
4. **Custom operators with non-built-in selectivity estimators** (CVE-2026-2004) — recreating them
   (dump/restore, branching) now requires superuser. Extension-installed operators (PostGIS,
   intarray) unaffected.

Timeline given: 2026-09-25 announce → 2026-09-28 new projects created on 15.19/17.11 → **2026-09-28
upgrade available in the dashboard for existing projects.** So the window is open now.

**Why it matters.** The worst failure mode here is silent: "ltree/btree_gist searches may silently
return wrong or incomplete results — no error is raised." A pipeline whose every stage transition
must write an `application_events` row cannot absorb a silently-incomplete index read. Separately,
item 4 breaks a future dump/restore or **branch** — which is exactly S13's per-PR preview-DB design.

**Concrete change.** Run the vendor's detection queries **before** upgrading, via the Supabase MCP
`execute_sql`, and record the result as an artifact. Then, in order: (a) decide on the upgrade
(Tier 2 — schema/infra, needs JB); (b) `REINDEX INDEX CONCURRENTLY <schema>.<index>;` for anything
flagged — online, no downtime, cannot run inside a transaction block; (c) if any `pgp_sym_*` values
exist, re-encrypt with `cipher-algo=aes256` and consider rotating the secrets — **Tier 3**, do not
touch without per-item approval. Likely outcome for this repo is "no ltree, no pgcrypto, no custom
operators, upgrade is routine" — but that is a claim to verify, not assume, and the mirror is too old
to answer it.

**Source.** [PostgreSQL 15.19 / 17.11 minor release](https://supabase.com/changelog/postgres-15-19-17-11-breaking-changes), Sep 25 2026.

## 7. `@supabase/middleware` 1.0 + `@supabase/server` 1.9.0 — vendor-maintained Edge Function auth boundary
**[Recommend: TRACK]**

**What's new.** Supabase, 2026-09-30. `@supabase/middleware` 1.0.0 on npm and JSR: "From 1.0 the
package follows semantic versioning: breaking changes ship only in a new major." MIT, a small engine
for per-request logic on Web Fetch handlers — `defineMiddleware` contributes one typed key to a shared
`ctx`, `pipeline([...], handler)` composes them, "duplicate keys and out-of-order prerequisites fail
to compile," and any middleware can return a `Response` to stop the chain. `@supabase/server` is built
on it, and `@supabase/server/middleware/*` exports `withClaims`, `withRequiredClaims`,
`withSupabaseClient`, `withSupabaseAdminClient`, `withPostgresClient`, `withPostgresAdminClient` —
"stable as of `@supabase/server` 1.9.0". The Edge Functions example notes "RLS scopes this query to
the signed-in user" for a client built via `withSupabase({ auth: 'user' })`.

**Why it matters.** This is a typed, compile-time-checked way to express non-negotiables #5 (every
query filters by `user_id`, no cross-user leakage) and #1 (RLS always on) *inside the Edge Functions*
— where the Gmail/Calendar scrapers drive autonomous stage transitions, and where a
service-role client is the easiest way to accidentally bypass both. The distinction the exports draw
between `withSupabaseClient` and `withSupabaseAdminClient` is exactly the distinction the repo
currently has to maintain by convention and code review. "Out-of-order prerequisites fail to compile"
turns an auth-boundary rule into a type error.

**Concrete change.** TRACK, not IMPLEMENT — two reasons. First, this would touch the auth boundary
and the Edge Functions on a 14.5-week-stale picture of both; an ADR comes before code. Second, it
partly overlaps `.claude/agents/supabase-security.md` and the S235 Security-role prompt, and those
should be reconciled first. Next step when GitHub returns: read the current Edge Functions'
client construction, then write `docs/adr/NNN-edge-function-middleware.md` weighing adoption against
the single-DB-client rule (non-negotiable #2 — `src/lib/supabase.ts` is the browser client; Edge
Functions are a separate surface, and whether that rule is meant to reach them is itself an
undocumented question worth settling in the ADR).

**Source.** [Supabase Middleware 1.0](https://supabase.com/changelog/supabase-middleware-1-0), Sep 30 2026.

re-encryption step or card 1's settings commit moves without per-item approval.

natively) and **5** (the only item with a security clock on it).
