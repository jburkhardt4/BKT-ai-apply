### 3. S193 — Frontier Red Team: measured multiagent failure modes (convergence, coordination collapse, turf wars)  [Recommend: TRACK]  · Theme 2

- **What's new:** Anthropic's Frontier Red Team published empirical failure modes of agent swarms, several measured inside Claude Code itself. Three findings: (a) **Low-variance convergence** — "18 out of 30 agents decided to create a git branch with the exact same branch name, 'mvp-game-loop.'" (b) **Coordination degrades as swarms grow** — merged-PR fraction fell as agents rose from 10 → 80 (this figure appears in the chart alt text; the prose attributes the differences primarily to **model generation**, not swarm size alone). Newer models "solved" conflict only by *not collaborating* — high file ownership, near-zero code sharing. Finding (b) argues the useful `/dispatch` wave width is small and bounded by disjoint file ownership, not by `MAX_CONCURRENT_SUBAGENTS` — though note the source attributes the degradation partly to model generation, so treat this as directional, not a measured ceiling for today's models. ### 5. S195 — TypeScript 7.0 stable (native Go port) — 8–12x faster `tsc`, and the repo is one major behind  [Recommend: IMPLEMENT]  · Theme 3

- **What's new:** TypeScript 7.0 shipped stable — a native Go port with shared-memory multithreading, typically **8–12x faster on full builds** (vscode 125.7s → 10.6s; playwright 12.8s → 1.47s) while using **6–26% less memory**. New parallelization controls: `--checkers` (default 4 type-check workers), `--builders` (parallel project-reference builds under `--build`), and `--singleThreaded`. Rebuilt `--watch` on a Go port of `@parcel/watcher`. Language server is LSP-based; failing LS commands down >80%, crashes down >60% vs 6.0. **The catch: 7.0 ships without a programmatic API** — 7.1 is expected to add it. Tools that import `typescript` directly (typescript-eslint, Volar, webpack loaders) must stay on 6.0. Microsoft ships `@typescript/typescript6` (provides `tsc6` + re-exports the 6.0 API) for side-by-side via npm aliases.

### 7. S197 — Vite 8 `server.forwardConsole` auto-enables when a coding agent is detected — already installed, currently unused  [Recommend: TRACK → cheap IMPLEMENT]  · Theme 2 (+ Theme 1)

- **What's new:** Vite 8's dev server can forward browser console output and unhandled runtime errors into the **dev-server terminal**. `server.forwardConsole` takes a boolean or `{ unhandledErrors, logLevels }`. Its default is **`true` when an AI coding agent is detected** (via `@vercel/detect-agent`), `false` otherwise. When `true` it forwards unhandled exceptions, unhandled promise rejections, and `console.error` / `console.warn`. Example: `forwardConsole: { unhandledErrors: true, logLevels: ['warn', 'error'] }`.
- **Why it matters for bk-ai-apply:** **The repo is already on `vite ^8.0.12` — this capability is installed and, as far as the mirror shows, unconfigured.** It closes the single most annoying blind spot in an agent dev loop: a Claude Code session running `pnpm dev` cannot see browser-side runtime errors, so a change that type-checks, lints, and passes unit tests but throws in the browser looks like success. Forwarding puts that error in the terminal the agent is already reading — no screenshot round-trip, no Playwright run, no MCP call. That is a materially cheaper feedback path than most of the Theme-1 tooling in the ledger, and it is free. Worth being explicit rather than relying on auto-detection, so behavior is identical whether a run is agentic or JB's own.
- **Concrete change:** One line in `vite.config.ts`:
  ```ts
  server: { forwardConsole: { unhandledErrors: true, logLevels: ['warn', 'error'] } }
  ```
  Set it explicitly rather than depending on `@vercel/detect-agent`. Note it in `docs/conventions/error-handling.md` so the agent loop knows browser errors surface in the dev-server terminal.
- **Risks / caveats:** (i) Start at `['warn','error']` — forwarding `log`/`info` on a chatty app will flood an agent's context window, which is the opposite of the intent. (ii) **Vite 8.0.11 had a real bug** here — `__BUNDLED_DEV__` / `__SERVER_FORWARD_CONSOLE__` passed through unreplaced in `/@vite/client`, causing a browser `ReferenceError` (vitejs/vite#22419). The `^8.0.12` floor already excludes 8.0.11, but confirm the **resolved** version in `pnpm-lock.yaml` is ≥ 8.0.12 before enabling. (iii) Dev-server only; no production or CI effect.
- **Sources:** Vite — Server Options, https://vite.dev/config/server-options; "Vite 8.0 is out!", https://vite.dev/blog/announcing-vite8.html (**2026-03-12**); implementing commit https://github.com/vitejs/vite/commit/2540ed06d0b6f93829d2d764b6a02f7dbfd14923; bug https://github.com/vitejs/vite/issues/22419.
- **Recommended action:** TRACK, but this is a **one-line change with an immediate agent-loop payoff** — promote to IMPLEMENT on approval. Older than the 30-week emphasis, surfaced now because verifying `package.json` proved the capability is present and idle.
