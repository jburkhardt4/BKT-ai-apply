### 1. `vercel curl` — first-party CLI that auto-handles deployment-protection for testing protected previews  `[Recommend: TRACK]`  *(Theme 1 / AI-UAT — extends S35, S94)*
- **What's new:** Vercel ships a **`vercel curl`** CLI command that "works like curl, but automatically handles deployment-protection bypass tokens for you." It lets automated tests / CI hit a **protected preview deployment** without manually threading a bypass secret or OIDC token into the request. (Docs page `vercel.com/docs/cli/curl`, last updated **2026-05-28**.)
- **Why it matters for bk-ai-apply:** The AI-UAT-against-Vercel-previews line (S03 auto-trigger, S35 automation-bypass, S94 Trusted-Sources OIDC) currently assumes the workflow constructs protected-preview requests by hand-managing the bypass secret/header. `vercel curl` collapses that to one first-party command — fewer places a long-lived bypass secret is echoed into CI logs, and a cleaner smoke-probe (`vercel curl <preview-url>/health`) before the heavier Playwright/Stagehand UAT run. Strictly simplifies S35; complements (does not replace) the S94 OIDC direction for the full UAT session.
- **Concrete change (narrow):** When `ai-uat.yml` is wired to a real Vercel preview, use `vercel curl` for the reachability/health pre-check and for lightweight authenticated probes, instead of a hand-rolled `curl -H "x-vercel-protection-bypass: …"`. Keep the OIDC path (S94) for the browser UAT session. Doc the choice in the AI-UAT runbook. No product-code change.
- **Source(s):** [Vercel CLI — `vercel curl` (docs, updated 2026-05-28)](https://vercel.com/docs/cli/curl); [Vercel Deployment Protection — automated/agent access](https://vercel.com/docs/deployment-protection/automated-agent-access).

### 2. Recompile gh-aw `*.lock.yml` to compiler **v0.86.1** (Aug 7) — absorbs firewall digest-pin-loss fix  `[Recommend: IMPLEMENT]`  *(Theme 2 / supply-chain — extends S113)*
- **What's new:** GitHub Agentic Workflows compiler **v0.86.1 (2026-08-07)** ships compiler safety fixes plus a fix for **recurring `gh-aw-firewall` digest-pin loss on `DefaultFirewallVersion` bumps**, new guided **`gh aw fix`** diagnostics (e.g. flags `tools.bash` allow-listing on engines that ignore it), **explicit end-marker syntax for inline skills/sub-agents**, and expanded engine defs. This is the first gh-aw release past the ledger's **v0.84.3 (S113, Aug 3)**.
- **Why it matters for bk-ai-apply:** The repo commits **three gh-aw `*.lock.yml`** workflows (agentic-pr-code-review, auto-rebase-merge, pr-comment-fixer). The firewall digest-pin-loss fix is a real supply-chain regression: a `DefaultFirewallVersion` bump could silently drop the SHA-pin on the firewall action, weakening the pin discipline S16/S113 established. Recompiling regenerates the lock files with the corrected pins and refreshed action digests. `gh aw fix` also gives a runnable lint for the committed workflows.
- **Concrete change (narrow):** In Codespaces, bump the gh-aw CLI, run `gh aw compile` for the three `.md` sources to regenerate their `*.lock.yml`, run `gh aw fix` to surface diagnostics, and review the digest-pin diff before commit. **Queued** pending GitHub access. No app-code change.
- **Source(s):** [github/gh-aw releases (v0.86.1, 2026-08-07)](https://github.com/github/gh-aw/releases); [GitHub Agentic Workflows — Weekly Update 2026-08-10](https://github.github.com/gh-aw/blog/2026-08-10-weekly-update/).

### 3. Supabase **pg-delta** declarative-schema engine + June auto-baseline `declarative sync --apply`  `[Recommend: TRACK]`  *(Theme 3 / repo + migration workflow — extends S26)*
- **What's new:** Since S26 carded the base declarative-schema workflow, Supabase shipped **pg-delta** — its own Postgres schema-diffing engine — as the experimental engine behind `supabase/schemas` + `supabase db diff` ([Public Alpha changelog #44938](https://supabase.com/changelog/44938-public-alpha-declarative-schema-management-with-pg-delta)). The **June 2026 developer update** then improved `supabase db schema declarative sync --apply` to **auto-provision and record the required platform baseline**, so a new declarative project needs less manual setup before its first apply.
- **Why it matters for bk-ai-apply:** The repo carries **34 hand-written migrations** and a hard non-negotiable — *"run `pnpm db:gen-types` after schema changes; never handwrite DB types."* A declarative `supabase/schemas` source of truth with pg-delta-generated migrations reduces hand-authored migration drift and pairs naturally with the generated-types + RLS-always-on invariants (a single declarative RLS-policy file is easier to review than diffing across 34 migrations). Alpha — evaluate on a Supabase branch first; **ADR before adopting** (this changes the migration authoring model). Peer of the RLS-testing line (S41/S100) and realtime-DDL guard (S134).
- **Concrete change (narrow):** Spike on a throwaway Supabase branch: export current schema into `supabase/schemas/*.sql`, run `supabase db diff` (pg-delta) to confirm it reproduces the existing migration state, and try `db schema declarative sync --apply`. If clean, draft an ADR proposing declarative schemas as the go-forward authoring model; do **not** convert the 34 migrations in place. No app-code change.
- **Source(s):** [Supabase Changelog #44938 — Declarative Schema Management with pg-delta (Public Alpha)](https://supabase.com/changelog/44938-public-alpha-declarative-schema-management-with-pg-delta); [Supabase Developer Update — June 2026 (#46689)](https://supabase.com/changelog/46689-developer-update-june-2026).
